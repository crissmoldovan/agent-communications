# 0.37.0: what the 0.36.0 security review left

0.36.0's review (`2026-10-27-workflows-design.md` §16) left six items for this release. The owner, 2026-10-28: "let's
make progress on all, if you need me to do anything let me know". This document decides each one. The 0.36.0 design
stays normative for everything it does not change.

Each section says what goes wrong today, what this release does about it, and the tests that prove it. The lead made
every call below; none needs the owner, unless marked.

## 1. Slow steps no longer hold up the event service (L3)

**Today:**
- The scheduler awaits `workflows.tick()` inside the owner's tick (`runtime/scheduler.ts` `#tick`).
- The engine runs each step's executor one after another (`runtime/workflow/engine.ts` `#tick`, up to 16 rounds).
- So one slow call delays everything else: `git worktree add` (up to 60 s), a relay call (10 s) or a judge (its deadline).
  The sources aren't polled, no target delivery goes out, and later ticks wait.

**This release:**
- **The owner's tick no longer awaits the engine's pass.** It calls `WorkflowEngine.pump()`, as it calls
  `EventDispatcher.pump()` since 0.36.0 (commit 7bfe3690). `pump()` starts a pass when none is running and returns at
  once. A pass that is running is never started twice, and the next tick pumps again.
- **A pass runs under the shared writer lease,** as the tick's own work does (`withEventWriterLease`), so a key rotation's
  exclusive lease still waits for it.
- **Steps of different runs run side by side,** at most 4 at a time. Two steps of one run never do. A run's steps keep
  their order, through the claim and the settle as today.
- **A pass has a budget:** it claims no new step after 5 seconds. A step already running finishes, bounded by its own
  deadline.
- **Unchanged:** revocation, cancel and disable-all still end runs at once, in their own transactions. A step the pass is
  running settles nothing once its run has ended (0.36.0, M7).

**Tests:**
- A find step whose relay never answers within its 10 s, beside a mail that arrives at the same time: the mail is polled
  and its delivery made while the step waits. Today the mail waits.
- 6 runs each at a slow step: 4 run at once, then the other 2. The scheduler's tick returns while they run.
- Two steps of one run never overlap, under a pass that runs 4 at a time.
- A key rotation waits for a running pass, and a pass started after it waits for the rotation.

## 2. Worktree records of purged runs (§16)

**Today:**
- An ended run's history is purged with its decision's metadata (90 days by default).
- A `workflow_worktrees` row in state `made` or `kept` is never purged. The folder may still be on disk, and project
  sessions read these rows (`madeWorktreesOf`).

**This release:**
- **The history sweep looks at such a row once its run is purged.** If the folder no longer exists, or is no longer a
  worktree of the project's checkout (by `git worktree list --porcelain` of the checkout, through the hardened runner of
  §3), the row is deleted.
- **A worktree still on disk keeps its row,** and Projects keeps showing it: it is the person's to remove.
- **At most 100 rows a sweep.** A row whose checkout can't be read stays for the next sweep.

**Tests:**
- A purged run's `made` row whose folder is gone: deleted.
- One whose folder is still a worktree: kept.
- One whose checkout can't be read: kept, and tried again.

## 3. Git in a folder a session can write to (§16) — a security fix

**Today (an independent review, 2026-10-28, HIGH):**
- A run's worktree shares the main repository's `.git/config`: its `.git` points into `.git/worktrees/<name>`, whose
  `commondir` is the main `.git`. A session working in the worktree can write that config, and can commit
  `.gitattributes`.
- Program-running keys it plants run as the person the next time the event service runs git in the project:
  - `core.fsmonitor`, during `worktree add` and `status`;
  - a filter driver's `smudge`, `clean` or `process`, during `worktree add`'s checkout, the cleanup's `status` and
    `worktree remove`;
  - `include.path` and `includeIf`, which pull either in.
  - `-c core.hooksPath=/dev/null` stops hooks, not these. Each was confirmed against the real runner.
- The runner also strips `GIT_CONFIG_NOSYSTEM` with every other `GIT_*`, so the system gitconfig is read (MEDIUM).
- The spec's "LFS filters come from the person's own config" holds only by scope: a planted filter is `local`.
- **What holds:** no hooks, no shell, no `GIT_*` from the environment, the worktree root's checks, never `--force`, no
  fetch or push. `worktree remove` deletes nothing outside the root.

**This release:**
- **A. The runner** (`runtime/git.ts`):
  - It sets `GIT_CONFIG_NOSYSTEM=1`, the one `GIT_*` it passes, and leaves the global config in play, which is where
    the person's LFS lives.
  - After `-c core.hooksPath=/dev/null`, it overrides every fixed-name key that runs a program:
    - `core.fsmonitor=false`, `core.sshCommand=`, `core.gitProxy=`, `core.pager=cat`, `core.editor=false`,
      `core.askpass=`, `core.alternateRefsCommand=`;
    - `sequence.editor=false`, `credential.helper=`, `gpg.program=false`, `gpg.openpgp.program=false`;
    - `uploadpack.packObjectsHook=`, `diff.external=`, `protocol.ext.allow=never`.
  - A command-line `-c` wins over the repository's config.
- **B. A config gate,** `assertSafeRepoConfig(folder)`.
  - **When it runs:** before every `worktree add`, `status` and `worktree remove` the event service runs for a run.
  - **How it reads:** it reads `git config --list --show-scope -z` through the hardened runner. `--list` resolves
    includes, and shows what they pull in at the including scope.
  - **What it refuses**, at `local` or `worktree` scope:
    - any `filter.*.clean`, `.smudge` or `.process`;
    - any `diff.*.command` or `.textconv`, and any `merge.*.driver`;
    - `include.path` and any `includeIf.*`. A conditional include may not apply where the gate reads but apply where
      git runs, a worktree's `gitdir:` for one, so the directive itself is refused.
  - **What it doesn't refuse:** the fixed-name keys of A. A neutralises them on every command, with no race, and
    refusing them would refuse ordinary repositories (a local `core.editor`, say).
  - **What it trusts:** the same names at `global` scope, the person's own machine. LFS set by `git lfs install` lives
    there and keeps working. LFS written into one repository's own config is refused, by name, like any planted
    filter. That is the lead's call: the refusal says to move it to the global config.
  - **The refusal** names the key and its scope, never its value. In the worktree step it is
    `refused` with `REPO_CONFIG_UNSAFE`; in the run view and the story: "the repository's own config names a program
    git would run (`filter.x.process`, local)".
  - `alias.*` is not refused: the event service runs no alias.
  - **Its boundary** (the re-review, 2026-10-28): the gate trusts the person's global config. It holds while a session
    can't write `~/.gitconfig`, which is outside its worktree. A session the person lets edit their home folder's git
    config is past what this gate can stop, and the README says so.
- **C. `worktree add --no-checkout`, then the gate again, then the checkout.**
  - A filter planted between the first read and the add never runs at the add. The second gate sees it before the
    checkout would.
  - `status` and `worktree remove` have no such split: the gate runs right before each. The residual race, a session
    writing config at that instant, is a known limit and is written in §14 of the 0.36.0 design.
- **`project scan`** runs the gate on each folder it lists. A folder that fails it is shown with the reason and the key,
  so the person sees it before choosing it, and it can't be added as a project's folder until fixed.

**Tests,** with the review's planted states as fixtures: real `git` over temporary repositories, in a stand-in home.
- **The planted states:**
  - `core.fsmonitor` at local scope runs nothing during the add or the cleanup;
  - a committed `* filter=x` with a local `filter.x.smudge`, then `filter.x.process`, and the same through
    `include.path`: each is refused by name, and no marker is written;
  - an `includeIf "gitdir:…"` naming the worktree is refused.
- **LFS:** `filter.lfs.*` in a stand-in global config is allowed, and the worktree is made; the same keys at local scope
  are refused.
- **The system config:** with `GIT_CONFIG_SYSTEM` pointing at a planted file, it has no effect.
- **The runner:** it builds every `-c` override of A on every argv.
- **The add:** with `--no-checkout`, a filter planted between the first gate and the checkout is refused, and writes no
  marker.
- **Kept:** `worktree remove` leaves a folder outside the root intact when the worktree is replaced by a symlink.

**Release:** 0.37.0 is a security fix release (`release-flags`). The changelog says plainly who was exposed: anyone
who approved a workflow that makes a worktree and starts a session in it, on 0.36.0. It says what to do: update. And it
says what a refused repository means.

## 4. `runs cancel --interrupt` interrupts at once (§16)

**Today:**
- The cancel ends the run at once (0.36.0, M7).
- But the interrupt of the session's turn waits behind the engine's pass, with the cleanup, so the answer waits too.

**This release:**
- **The interrupt is asked as soon as the run has ended,** not behind the pass. A session's turn comes from the session
  dispatcher, not from a step, so waiting caught nothing more. `interrupted` still says whether it happened.
- **Only the cleanup waits for the pass** (a worktree's `remove-if-clean`), so it finds what the pass's step left.

**Tests:**
- With a pass gated in a slow step, `runs cancel --interrupt` answers, with `interrupted: true` from the stand-in relay,
  before the gate opens.
- The cleanup runs after it opens.

## 5. Describe it shows the person's own values in its questions (§16)

**Today:**
- A second round sends the draft with placeholders (`/redacted/folder-1`, …), and restores them in the draft it returns
  (0.36.0, M5).
- But a question or a choice the model writes keeps any placeholder it names, so the person reads `/redacted/folder-1`.

**This release:**
- **Placeholders are restored in each question and choice the result returns.** The same placeholders are used as for the
  draft of that round.
- **Answers are redacted before they go back.** On the next round, the person's answers pass through the same redaction
  as the draft, so a choice that names their folder goes back as its placeholder.

**Tests:**
- A model question naming `/redacted/folder-1` reads the person's folder.
- Choosing that choice sends the placeholder on the next round, never the folder.

## 6. An approval's lines name the limits (§10.2, §16)

**Today:** `describeFlow`'s numbered lines don't name `flow.limits`; only the approved JSON under them holds the limits.
§10.2 says the lines name "the limits".

**This release:**
- **`describeFlow` ends with one line of the flow's limits,** in plain words. For example: "At most 6 runs an hour, 2
  at a time; at most 2 sessions started, 30 Linear writes and 120 events an hour; at most 5 worktrees a day; a run
  ends after 3 days." It names each of
  `flow.limits` as written, defaults included, in a fixed order.
- **Its numbering follows the effects.** The app's Approve view and the terminal preview show it, as they show every
  line.
- **The preview fixtures that pin a flow's lines gain the line.** Their pins are recomputed from the new files, and no B3
  guard's anchored line changes.

**Tests:**
- The owner example's approval ends with its limits line, exactly.
- Every limit's word and value appear, defaults too.
- A flow with a non-default limit names its value.
