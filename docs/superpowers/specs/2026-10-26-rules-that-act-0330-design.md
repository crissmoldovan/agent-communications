# 0.33.0: rules you edit, analyse, and that act (Linear and agent sessions)

Status: draft, 2026-10-26. Written under the owner's `/goal` of 2026-10-26 and their word after reviewing the
prototype: "perfect … Let's proceed by specking out and implementing everything, but we need to also consider releasing
everything."

The prototype's row 2 holds the screens: `RuleEdit`, `RuleEditText` and `RuleAnalyse` in
`docs/prototypes/2026-10-26-0320/`. The claude-stream facts were read on 2026-10-26 from `cueplusplus/claude-stream` at
40ea7f57 (`docs/agent-relay/api-contract.md`). **O** = the owner's decision, **L** = the lead's call.

## 1. Intent

The owner, 2026-10-26:
- **On editing:** "I should have a visual way of editing a rule or a text-based way of editing a rule. Any of them will
  have an Analyse, and that will create a more enriched version of the rules … each of the rules (like when, what
  should happen, what should do, and so on) should maybe be optimised and passed through a prompt optimizer or text
  optimizer that is dedicated to those specific use cases."
- **On actions:** "Some of the rules may have some target actions. One target action would be 'add to Linear' … Another
  … 'post message to session,' 'starting session,' or 'find session.' If it's not present, create a new session … if
  the session is busy, enqueue it … the ability to pass on a more complex payload or context … data or extra text that
  is either generated by an LLM, fixed by us, or just something derived from the inputs or any other external factor.
  Currently, we cannot handle that."

Today a rule is written by an agent and approved at the terminal or in the app. Its targets can only record (dry-run),
send out (webhook, SSE) or hold for someone (the queue, a lane). This release lets the person write and improve rules in
the app, and lets a rule act: add a Linear issue, or hand the message to an agent session with the context it needs.

## 2. Goals, non-goals, anti-goals

**Goals**
- **Edit a rule in the app**, visually or as text. Either makes a new version, which the person approves in the app,
  while the old version keeps running until then.
- **Create a rule** in the app the same way.
- **Analyse** a rule, or a draft, and get suggestions per part, each with before, after and why. They come from
  content-free history on this Mac and from part-specific optimisers.
- **A Linear target** that adds an issue.
- **An agent-session target:**
  - it finds a session by folder or lane, or starts one, and queues the item while the session is busy;
  - it gives the session a prompt built from fixed text, the rule's mapped fields, model-written text and a file.

**Non-goals (this release)**
- Web addresses or command output as context: they are new egress and execution surfaces, and come later.
- Linear OAuth (a personal API key first), and Linear comments or updates (create only).
- A session view with its conversation: that is claude-stream's console.
- Interrupting a busy session: claude-stream refuses a second prompt while one runs (409), and nothing here works
  around that.

**Anti-goals: it fails if:**
- **Analyse sends message content anywhere.** It reads only the rule and counts.
- **An edit takes effect without the person's approval**, or the old version stops before the new one is approved.
- **A session or Linear receives a field the approved rule doesn't map,** or sender text outside the untrusted-content
  envelope.
- **An agent can write and approve its own rule from the app's paths:** the app's edit and approve are the person's,
  refused to agent markers and inside MCP.

## 3. Decisions

### 3.1 Editing makes a version, approved like any other (L)
- **The visual and text editors produce the same canonical rule document.** The app submits it with the existing
  `rule update <id>` or `rule create`, reading the document from stdin. The result is D2's `approvalRequired` with its
  preview.
- **The person approves it in the app** with the typed challenge the app already uses for D2 activations. The prototype
  shows it: "Type invoices to approve".
- **The old version keeps running until the new one is active.** That is D2's existing supersede.
- **The editors are the person's:** the app runs them as the person. `rule update` and `rule create` from MCP keep their
  existing agent path, which needs the person's approval anyway.
- **Fields the visual editor has no control for** (rare retention, mapping or AST shapes) show as "edited as text" and
  stay untouched.

### 3.2 The rule as text (L)
- **A small rule language**, `packages/events/src/rule-text/`, with `parseRuleText(text): CanonicalRuleDraft` and
  `printRuleText(doc): string`. Its grammar is the prototype's: `when`, `match any|all`, `ask`, `then`, `queue`,
  `session`, `linear issue`, `webhook`, `dry run`, `keep`, `at most`.
- **It round-trips:**
  - `parseRuleText(printRuleText(doc))` deep-equals `doc` for every rule fixture in the repository;
  - printing is stable;
  - a property test over generated documents checks both.
- **The canonical JSON stays what is approved.** The text is a view. An "Advanced: JSON" tab shows the canonical form
  read-only.
- **Checks as you type:** a parse error with its line, an unknown account or lane, an integration not connected, a file
  outside the allowed folders.

### 3.3 Analyse (L)
- **`rule analyse <id> [--draft -] --json`** runs in the event service, CLI only (the person's view, refused inside
  MCP). It returns `{ suggestions: [{ part, before, after, why, evidence }] }`. It never applies anything: the app puts
  an applied suggestion into the editor, and the person still approves the version.
- **What it reads:** the rule or draft document, and content-free counts for the rule over 30 days:
  - matches;
  - the judge's answers and their spread;
  - outcomes per decision;
  - per sender address *domain*, matches and judge outcomes;
  - queue items done or dismissed, against the judge's score.

  It reads no subject, body or full address.
- **Deterministic suggestions** (no model):
  - a sender domain the judge always said no to → an exclusion condition;
  - kept against dismissed scores → a judge bar;
  - a rule that never matched in 30 days → say so.
- **Model suggestions:**
  - **the judge's question,** against TypeSafe's guidance for System One questions: one yes-or-no about one fact,
    naming who asks for what;
  - **session context text,** through a prompt optimiser with a fixed brief for agent task prompts: a task, steps,
    limits, and what to do when unsure;
  - **a Linear title template.**
- **Where the model runs:** on the provider the person picks among those with keys (§3.2 of the 0.32 design):
  OpenRouter (default model `anthropic/claude-sonnet`, the current one OpenRouter lists) or a new `anthropic` provider
  key. Only the rule's own text and the counts are sent, and the screen says so with the provider's name.
- **Analyse is a person's act.** It runs only when they press it, and it is never scheduled.

### 3.4 The Linear target (L)
- **The document:** `{ kind: "linear", team: { id, key }, title: Template, description: Template, labels: [{ id,
  name }], assignee: "me" | { id } | null }`.
  - A `Template` is either a text with `{{field}}` slots naming the rule's mapped fields, or a generator (§3.6).
  - The D2 preview names the team, labels and assignee, and which fields fill the title and description.
- **The key:** a Linear personal API key, kept with the other provider keys (`provider key set linear`), and connected
  in Settings → Integrations. Integrations shows the workspace and teams the key can see.
- **The network:** the allow-list gains `api.linear.app`, the GraphQL endpoint only.
- **Delivery** creates the issue (`issueCreate`). The delivery records the issue's id and URL, content-free, and
  Deliveries links to it.
- **Failures** retry as webhooks do: a rate limit or 5xx retries, and a 4xx fails with its error code.

### 3.5 The agent-session target (L)
There are two kinds of session, and the target reaches either.
- **A window the person opened**, such as Claude Code in a terminal or VS Code, bound to a lane. 0.31's lanes already
  wake it through an MCP task. The target `{ kind: "session", find: { lane } }` is a lane queue item, as today.
- **A session claude-stream runs:** `{ kind: "session", find: { folder } | { lane }, ifNone: "start" | "queue-only",
  provider: "claude" | "codex", mode: <requestedMode>, ifBusy: "queue" | "queue-only", context: ContextPart[] }`.
  - **The relay:** Agent Comms is a client of the relay the person already runs.
    - Settings → Integrations → "Agent sessions" names the relay's home: claude-stream's default, or the Pilot app's.
    - The event service reads `control.token` from it as the same user. It never prints the token or puts it in argv.
    - Loopback only, as the relay requires.
  - **Find:** a session whose realpath `cwd` equals the folder, or whose `nativeSessionId` equals the lane binding's
    Claude Code session id. Several match → the most recently active.
  - **None:**
    - `start` creates `POST /v1/sessions { provider, cwd, requestedMode }`, then `POST /v1/sessions/:id/runs { prompt,
      startId }`, where `startId` is the delivery's id, so a retry is idempotent;
    - `queue-only` leaves it in the Queue.
  - **Busy:** the relay refuses (409) or reports `activeRunId`. With `queue`, the item waits in a new per-session queue
    (`session_queue`, in the event service's database). The event service follows the relay's event stream (SSE,
    resumed with `Last-Event-ID`) and posts the next item when the run ends. With `queue-only`, it waits in the Queue.
  - **The mode** is fixed in the target document and named in the D2 preview, for example "the session may ask before
    acting". The default is the relay's most restrained mode.
  - **The folder** must be inside the relay's allowed roots. If it isn't, the target refuses at activation, naming the
    folder.
- **Disclosure:** the D2 preview says plainly that matches' mapped fields and the listed context go to a Claude Code or
  Codex session in the named folder, which can act with the named mode.

### 3.6 Context: what a session (or a Linear issue) is given (L)
A target's `context` is an ordered list. Each part is labelled in the prompt by where it came from.
- **`{ text }`:** fixed text the person wrote. It is rule-author text, shown in the preview.
- **`{ fields: [pointer] }`:** the rule's mapped fields only. Sender-written values go inside the untrusted-content
  envelope.
- **`{ generate: { provider, model, instruction, from: [pointer] } }`:**
  - a model writes text from the named mapped fields, at dispatch;
  - the preview names the provider and which fields it receives;
  - the output is sender-derived, so it goes inside the envelope;
  - it has a token cap and a timeout, and on failure the part is left out with a note.
- **`{ file: path }`:** a file the person keeps, read at dispatch.
  - It must be under an allowed folder (the relay's allowed roots, or a folder the person adds).
  - It is capped at 64 KB, and missing → a note.
  - The preview names it.

**The prompt** sent to a session is a fixed frame, never free-form:
"[Agent Comms] The rule <id> passed you a message from <channel>/<account>." It is followed by each part with its label.
Sender material sits in the envelope, and the frame ends with the rule's instruction, if any.

### 3.7 Commands and parity
- **Both CLI and MCP:** `rule create|update` (existing; a draft from stdin) and `provider key set|remove|list linear`
  (0.32's command, with a new provider).
- **CLI only** (the person's view, each an exception row): `rule analyse`, `rule text print|parse` (for the app's text
  editor), `session-queue list` and `session-queue drop <id>`.
- **The app:** allow-list rows for each, with their arguments checked in Rust.

## 5. Questions for the owner (with the lead's default)

1. **Linear:** a personal API key first, OAuth later. Default: yes.
2. **Analyse runs on OpenRouter** with a Claude model, using the key you already added, or on an Anthropic key if you
   add one. Default: OpenRouter.
3. **A busy session:** queue the item until the session is free, or leave it in the Queue; there is no "interrupt".
   Default: queue.
4. **Outside context** this release: files only; web addresses and command output later. Default: yes.

## 6. Known limits

- **On Windows and Linux, changes go through a terminal.** Nothing there attests that the app started a command, so
  the person-only changes — judge setup, a provider key set or removed (Linear's too), Settings → Integrations → Agent
  sessions, a rule's approval — are refused from an origin nothing attests (`APPROVAL_REQUIRED`, exit 10,
  `details.reason: ORIGIN_UNATTESTED`, audited as `desktop-app (unattested)`) by the CLI and by the owner, and are
  done at an interactive terminal; the app offers Do it in Terminal. `approvedVia: app` therefore means the attested
  app. Analyse changes nothing and keeps its rule: the attested app, an interactive terminal, or, there, the app
  unattested. The owner still takes the origin label as a same-user control client declares it (a speed bump against
  agents, not a boundary).

- **A window the person opened** (not one claude-stream runs) can't be started or sent a prompt by the relay. It is
  reached through a lane wake (0.31), and the target says so.
- **Codex windows** are reached only when claude-stream runs them, or with `codex --remote`, which is experimental there.
- **claude-stream's packages are unpublished.** Agent Comms speaks its documented HTTP API (`/v1`, `schemaVersion: 1`),
  checks `GET /v1/relay` for `protocol: 1` and the capabilities it needs, and refuses, saying why, when they're absent.
