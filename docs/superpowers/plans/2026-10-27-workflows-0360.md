# Workflows 0.36.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship 0.36.0. In it, every workflow is one object in one list, drawn on a canvas or written as text:
- a workflow branches, waits, routes to a project, finds or starts a session (optionally in a new worktree), and creates
  and closes a Linear issue;
- any step can raise namespaced CloudEvents to approved subscribers, live on this Mac (SSE or WebSocket) or by signed
  webhook;
- an event can start another workflow.

**Architecture:**
- **The document.** A workflow stays a rule version with an optional `flow`. Its graph, its step event catalogue and its
  name grammar are pure code in `@agentcomms/events`, shared by the event service and the app.
- **The engine.** `WorkflowEngine`, inside the event service's owner, runs steps through one executor per kind. Waits are
  database rows, and every state change goes through one transaction. Engine, projects, sessions, worktrees and events
  plug in through `runtime/workflow/contracts.ts`.
- **The app.** The desktop designer is React Flow through `@cueplusplus/ui/flow`, over the same document.
- **The order:** a short Track 0 lands the shared contracts and the schema; six tracks then build in parallel worktrees;
  Track G integrates and runs the full chain once.

**Tech Stack:**
- TypeScript on Node ≥ 22.16, `node:sqlite` and `node:test`, in `packages/events` and `packages/events-daemon`;
- React 19 and `@xyflow/react` ^12.11.3 through `@cueplusplus/ui` 0.34.0, with vitest and Playwright, in `apps/desktop`;
- Rust (Tauri) for the app's allow-list;
- biome; pnpm.

**Spec:** `docs/superpowers/specs/2026-10-27-workflows-design.md` (normative for 0.36.0). Read §0 and W1–W36 before any
task. Also read:
- `AGENTS.md` and `CONTRIBUTING.md`;
- for `packages/events`, the local-event-emission design's Appendix A, which stays unchanged;
- `docs/superpowers/specs/2026-10-26-rules-that-act-0330-design.md` for the session and Linear targets.

## Review Focus

- **A message whose sender text looks like an event name or a step id** (`acme.client-asks.issue.created`, `{{steps.x}}`).
  It must stay data: never a pattern, a slot or a branch.
  - T0.1's `isEventSegment` refuses non-literal input.
  - D2 asserts the sentinel sender text never appears in any automatic event's bytes.
- **The person turns a subscriber off, or rotates its token, while a run raises events.** No frame may leave after the
  revoke commits.
  - D3 and D4 test a frame written after `subscriber remove` returns, on SSE and WebSocket.
  - D5 tests a webhook delivery claimed before the revoke and fenced after it.
- **The relay restarts, or its journal resets, while three runs wait** (a turn's end, a free session, a timeout). Each
  wakes once, with the right outcome, after the reconnect. B4 tests all three in one owner across a fake relay reset.
- **A workflow edited in the designer while one of its runs is mid-flight.** The run keeps its version's graph and the
  run view draws that version, not the new draft.
  - B6 asserts `runs show` names `ruleVersion` and returns that version's steps.
  - F1 asserts the run view fetches `workflow show --version <runVersion>`.
- **A straight-line workflow, opened, untouched and saved.** It must make no new version and no approval.
  - E4 asserts Save is off and no `eventsRuleUpdate` call is made.
  - A3 asserts `flowOf` never writes `flow` into the document it reads.

### I5. Closed outputs (the `output` a settled step writes; events carry them, minus paths)

**What a step stores and what its events carry are two sets (T0.1).** The table below is the stored `output`. An event's
