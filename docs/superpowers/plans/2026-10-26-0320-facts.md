## A. "I do not see any MCP section on the left sidebar"

**Today**
- The sidebar has nine sections plus Settings: Overview, Queue, Accounts, Approvals, Activity, Agent, Updates, Events, Doctor (`apps/desktop/src/copy.ts:23-35`; icons `Shell.tsx:20-31`; rendered `Shell.tsx:85-88`). None of them is about MCP.

The Doctor screen renders `check.detail` as plain text (`screens/Doctor.tsx:170`).

**Data that already exists**
- `agentcomms channels --json` → `channelsAvailable` (CLI `packages/core/src/cli.ts:1279-1283`, MCP `comms_channels_available`, `capabilities.json:455-461`). Read-only, and never returns an entry's `env` (`operations/servers.ts:1126-1131`).
  - Per server: `channel`, `kind` (channel/service), `label`, `package`, `serverName`, `installs`, `installed`, `runtimes[]`, `onPath`, `registered[]` (`servers.ts:1073-1092`).
  - Per registration: `client`, `name`, `scope` (user/project), `path` (the config file), `launcher` (managed/npx/local/other), `version`, `narrowing`, `pathPins`, `missing` (an entry whose file has gone), `behindCore` (`servers.ts:1051-1071`).
  - Top level: `unreadable[]` client configs (`:1094-1100`).
  - The event service's MCP server is included: `SERVERS` holds the channels, then the services (`core/src/channel-servers.ts:44-47`).
- Clients it scans: claude-code (`~/.claude.json` and per-project `.mcp.json`), cursor, codex (`CODEX_HOME/config.toml`), gemini, claude-desktop and vscode (paths per OS). See `core/src/mcp-clients.ts:73-110,421-435`. The install-target vocabulary is `CLIENTS` (`servers.ts:96-104`).
- Changes already exist as operations: `mcp install` (`serverInstallChange`) and `mcp prune` (`serverPruneChange`), both approval-gated changes (`capabilities.json:631-680`). Per the core server's instructions, a new server only appears once the client restarts.
- Per-client recency, from activity (0.29): every line carries `session.client = {name, version}`, which is what the MCP client *said* in `clientInfo`, not proof (`core/src/activity.ts:67-71,120-130`). `activity sessions` returns `client`, `firstSeen`, `lastSeen`, `channels`, `accounts` and counts per session (`activity.ts:433-446`), and the app already calls it (`Call::ActivitySessions`). - No `channels` call in the app: one new read-only row (`channels --json`, core).
- Activity's `client.name` is self-reported (fixtures use `claude-code`). Nothing maps it to the `CLIENTS` ids, so "cursor last used 2h ago" needs a mapping table, a guess for non-Claude clients. A client whose calls touched no account data has no recency at all.
- "Restart needed" is unknowable: nothing records when a client last started a server.

**Feasibility:** high. An "MCP" screen lists each client's servers (scope, launcher, version, behind core, missing file) and the unreadable configs. Install and prune go through the approval-to-terminal path (DA10). "Last used" can only be approximate.

## B. Events → Rules: "mail subject version 1 state active and approval and activation"

**What the tab renders:** a table of raw columns: Rule (`rule_id`), Version, State, Approval (`approval_id`), Activation (`authorization_activation_id`) and Digest (12 characters) (`screens/Events.tsx:115-122`). It comes from `Call::EventsRules` → `rules list` (`allowlist.rs:798`). Rows have no click handler (`ListTable`, `Events.tsx:145-221`). One row appears per *version*, including inert and superseded ones (`Events.tsx:611-612`). So the owner saw his rule `mail-subject`, v1, `active`, plus two opaque ids.

**`rules list --json` per row:** the snake_case SQL row `{rule_id, version, digest, state, approval_id, authorization_activation_id}` (`events-daemon/src/runtime/owner.ts:1923-1929`). It carries no channel, event type, accounts, targets or times.

**`rule show <rule-id>`:** the CLI command exists (`events-daemon/src/cli/program.ts:399-402`), and so does MCP `events_rule_show`. It returns an array with one entry per version: `{document, digest, state, approval_id, authorization_activation_id}`, where `document` is the full parsed canonical rule (`owner.ts:1931-1945`). The wire op is marked `desktopCallable: true` (`runtime/control-operation-registry.ts:19`), but the app's allow-list has no row for it. The table also stores `activated_at`, `superseded_at` and `revoked_at` (`store/schema-v1.ts:31-48`), but `rule show` does not return them.

**What the words mean (design `docs/superpowers/specs/2026-10-05-local-event-emission-design.md`)**
- **state:** a version is either *inert* (never activated; state is null, "absence is not a fourth state") or one of `active` (the version the rule's pointer names), `superseded` (replaced by an exact new version, and its retained work still runs out its retention) or `revoked` (disabled, removed or tightened away; work cancelled). Design `:453-460` and `:1465-1473`.
- **approval:** the core `disclosure` approval the person gave at the terminal (or in the app by typed challenge): a *standing disclosure authorisation* for future, unseen messages (`:142-152`).
- **activation:** `authorization_activation_id`, the record binding that approval to this exact version; it fixes the version's lineage (`:1467-1469`).
- Neither id means anything to a person. Both are for audit.

**The rule document (what a summary has to describe)**, from `CanonicalFullRuleDocument` (`events-daemon/src/domain/activation-documents.ts:101-117`):
- `ruleId`, `version`. There is no human name or description field: the id is the name everywhere (`runtime/queue.ts:699-700`).
- `source`: `{channel, accountIds[], options}`. The options are, for Gmail, `labels` (list, `inbox` or `any`) and `includeSpamTrash`; for Slack, `conversations[]`; for Resend, `kinds[]`; for WhatsApp, `chats[]` or `all-allowed` (`domain/source-options.ts:4-21`). Accounts are ids, so a summary has to resolve them to aliases.
- `event`: `{type, version}`, e.g. `gmail.message.received`.
- `condition`: the deterministic tree (all/any/not, exists, equals, contains, startsWith/endsWith, in, gt…lte, domainIs) (`packages/events/src/conditions/types.ts:7-27`). **A renderer already exists:** `describeCondition()` produces sentences such as "/subject contains "invoice" (case-sensitive)" (`packages/events/src/conditions/describe.ts:14-37`), but it speaks in JSON pointers.
- `agentic?`: an optional judge question, with `inputs` (pointers), `threshold`, `onUncertain` (no-match or hold) and per-rule limits (`conditions/types.ts:60-72`).
- `mapping`: which event fields leave the service, as a mapping AST. `cloudEventType?` is an override.
- `targets[]`: one of `dry-run {retentionMs}`, `webhook` (URL or secret-URL descriptor, approved address set, signing, ordering, retry limit), `sse` (subscriber, origins) or `queue {retentionMs, show: summary|minimal, lane?}` (`activation-documents.ts:45-53`, `domain/queue-target.ts:23-35`). Plus `subscribers[]` and `judges[]`.
- `deliveryRateCap`: default 60 per rolling hour.
- `retention`: ingest, hold, delivery, dry-run (24h at most), SSE replay, dead-letter, decision metadata and queue, all in milliseconds (`activation-documents.ts:64-77`; defaults at design `:272-281`).

**Gaps:** no `rule show` call in the app, no plain summary, no rule name, and the list lacks type, channel and targets. Even the terminal approval preview prints `Preview <canonical JSON>` (`operations/b3-contract.ts:1531-1541`).

**Feasibility:** high. Add a read-only `eventsRuleShow{ruleId}` row (Rust checks the id's grammar, as for `lane`). Clicking a row opens a detail page:
- a sentence such as "When a Gmail message arrives in *cue/gmail* (Inbox) whose subject contains 'X' → queue it / log it for 24h; at most 60 an hour; kept 7 days";
- the version history, with times once `rule show` returns them;
- "Approved at the terminal on …" in place of the raw ids.

This needs field labels for the catalogue pointers and alias resolution. Condition operands stay `UntrustedText`.

## C. Events → Deliveries: "next try is always 1970 … where is this log?"

**What the tab renders:** Delivery, Rule vN, Target vN, Account (the raw `accountId`, no alias), State, Attempts, Next try, Expires. It shows the 100 most recent, sorted by expiry (`Events.tsx:124-133,139-142,69`). The rows are not clickable.

**Why 1970 appears (a real bug):**
- `moment()` formats any number with `<When>` (`Events.tsx:101-103`), and `new Date(0)` is 1 Jan 1970 (`components/When.tsx:10-13`).
- Every delivery is inserted with `next_at = 0`, meaning "due now" (`events-daemon/src/runtime/decisions.ts:212` and `:361`).
- When a delivery completes, the **dry-run, queue and SSE dispatchers set `state='delivered'` without clearing `next_at`** (`runtime/dispatcher.ts:571`, `runtime/queue-dispatcher.ts:320`, `runtime/sse-dispatcher.ts:340`). The webhook dispatcher does clear it (`next_at = NULL`, `runtime/webhook-dispatcher.ts:765`), and so do every cancel and expiry path.
- `deliveriesList` returns `nextAt: number|null` as stored (`runtime/b3-operator-control.ts:434-460`). A delivered dry-run or queue row therefore comes back as `0`, not `null`.
- The app's fixture uses `null` (`apps/desktop/src/test/fixtures/events-deliveries.json:12`), so no test sees the 0.
- Fix either side: the app should show "Next try" only for `queued` or `retryable` rows, and/or the three dispatchers should set `next_at = NULL`.

**`deliveries list --json` per row:** `deliveryId, accountId, ruleId, ruleVersion, targetId, targetVersion, subscriberId, subscriberVersion, attempts, nextAt, expiresAt, state, switchGeneration, deadLetterExpiresAt` (`b3-operator-control.ts:434-460`). It does **not** return the target **kind** (dry-run, webhook, SSE or queue), even though `deliveries.target_kind` exists (`store/migrations.ts:794-797`). It also omits `last_error_code`, `last_status`, `decision_id` and any creation or delivered time. States: queued, retryable, disclosing, delivered, dead-lettered, retention-expired, cancelled, content-unreadable, in-flight-at-disable, in-flight-at-account-removal (`store/schema-v1.ts:256`).

**Show commands:** there is no `delivery show` and no `event show`. `delivery` has only `retry` and `drop` (`cli/program.ts:681-689`). `held list` lists held decisions. `rule test-retained <event-id>` exists (`program.ts:435`).

**The "log" is the dry-run target**
- It is stored in the `dryrun_log` table of `<state>/events/events.sqlite` (`runtime/paths.ts:66-70`). Each row holds `delivery_id, rule_id/version, target_id/version, event_id, account_id, encrypted_record` (the exact would-be CloudEvent bytes), `delivered_at` and `expires_at`, and the schema caps the age: `expires_at - delivered_at <= 86400000` (`store/schema-v1.ts:264-277`). It is purged at expiry (design retention table `:1867`).
- A person reads it with `agent-events dryrun list` and then `agent-events dryrun show <delivery-id>` at an interactive terminal. Each record is rendered inside the untrusted-content envelope (`targets/dry-run.ts:29-38`).
- The `deliveryId` the app already shows is exactly the argument `dryrun show` takes.
- `dryrun list` returns `{deliveryId, ruleId, ruleVersion, targetId, targetVersion, eventId, accountId, deliveredAt, expiresAt}`, which is content-free (`runtime/dispatcher.ts:42-56`).

**What stops the app reading it**
- Both `dryrun list` and `dryrun show` call `assertHumanTerminal(env, streams, json)` (`cli/program.ts:707-718`). That function refuses any agent marker and refuses whenever the process cannot prompt *or* `--json` is set (`targets/dry-run.ts:11-26`).
- The app always runs with `--json` and a closed stdin, so it is refused, even for the content-free list.
- The owner side would allow it: both wire ops are `desktopCallable: true` (`control-operation-registry.ts:84-85`).

**Why the gate exists, and the precedent**
- Design D7: "Only a person at the terminal **or in the app** may read it, through D3's untrusted text renderer; no MCP result … contains its payload" (`:1219`). The CLI gate is stricter than the design.
- The queue's Q1 lets the app read content with `--json` and only refuses inside an MCP server's process (`assertNotMcpServer`), since an agent with a shell runs as the person anyway. It left "`dryrun show`'s terminal-only gate … unchanged" (`2026-10-25-action-queue-design.md:153-161`; `program.ts:720-721,741-760`).

**Feasibility**
- The 1970 fix: trivial.
- A delivery detail panel from the list row: easy. It gets better if `deliveriesList` adds the target kind and the last error (a small owner change).
- A dry-run record in the app needs a spec decision. Either move `dryrun list/show` to Q1's gate and add two allow-list rows, rendering the event as `OutsideText`, or add a "Show in Terminal" `TerminalCommand`, as `laneBind` does (`ipc.ts:203-215`).
- Content older than 24h is gone by design.

## D. Per message: arrived → matched → judged → delivered/queued → read by → replied/acknowledged

**What each store keeps, and the join keys**

| Store | Per-message key it keeps | Where | Retention |
|---|---|---|---|
| Ingest (one row per observed event) | `event_id`, `type`, `account_id`, `occurred_at`, `observed_at`, and `dedupe_key` in cleartext: Gmail `["<historyId>","<messageId>","received"]`, Slack `<channelId>/<ts>`, WhatsApp `<chatId>/<messageId>`, Resend `emailId` | `store/schema-v1.ts:207-217`; keys at `packages/events/src/catalogue/definitions/gmail.ts:187-190`, `slack.ts:88`, `whatsapp.ts:107`, `resend.ts:121` | Not purged except on account removal (`runtime/account-fence.ts:209`) |
| Decisions (one per event × rule version) | `event_id`, `rule_id/version`, `outcome` ∈ matched / no-match / mapping-rejected / retention-expired / hold; the judge value is in metadata | `schema-v1.ts:226-240`; `runtime/decisions.ts:16` | Decision metadata 90 days |
| Deliveries | `decision_id` → event; target; state; attempts | `schema-v1.ts:241-263` | Row stays; payload purged |
| Queue items | internal `event_id`, `decision_id`, `delivery_id`; `state` open/done/dismissed + `state_at`; `arrived_at`; Gmail `messageId` or Slack `workspaceId/channelId/threadTs` only inside the encrypted content, and only if mapped with `show: summary` | `store/migrations.ts:811-837`; `domain/queue-target.ts:278-291,343-360` | 1–30 days (content), one more retention (row) |
| Lanes | binding (session id / activity key, folder, client, since); a wake's high-water mark **in memory only** | `migrations.ts:855-878`; `runtime/lanes.ts:33-36,237-240` | — |
| Activity log (core, 0.29) | per call: session (key, folder, client), `operation`, `items[{id, subject, from, conversation}]`, `approvalId`, `recipients`, `told{rule,target}` | `core/src/activity.ts:89-100,149-171` | 30 days by default (`activity-settings.ts:22`) |
| Slack ack ledger | `channel`, `ts`, `thread`, `sender`, `standingId`, `childId`, and an outcome line sent / failed / unknown | `core/src/standing-ledger.ts:9-50` | Append-only, never removed |
| Audit log | send: `approvalIds`, `draftIds`, `messageIds`, recipients | `gmail/src/operations/send.ts:1494-1505`; `core/src/audit.ts:12-46` | — |

**What each activity line records, by channel**
- Gmail reads record the **messageId** of each message: `gmail.message.read` (`gmail/src/operations/read.ts:370-377`) and every message of a `gmail.thread.read` (`read.ts:280-290`). A search records messageId or **threadId** depending on its kind (`search.ts:340-341`). These join to the event's `dedupe_key`.
- **Gmail replies are not linked.**
  - `gmail.draft.reply` takes the `messageId` it replies to, but records only `{draftId, subject}` (`drafts.ts:478-485,240-243`).
  - `gmail.send.execute` records `sentMessageId ?? draftId`, subject and recipients (`send.ts:1206-1217`). It does not record `threadId`, although `SendResult.threadId` has it (`send.ts:159`). The audit record has no thread either (`send.ts:1499-1504`).
- Slack reads record the message `ts` plus `conversation`. That is the channel **name** for history reads (`slack/src/activity.ts:127-132`) but the channel **id** for thread reads (`:135-138`). The event key uses the id, so history reads join only after resolving the name.
- Slack posts record `{posted ts, channel id}` and no `thread_ts` (`activity.ts:258-269`), so a reply cannot be tied to the message it answered.
- **Slack `ack`** (`slack_ack` / `agent-slack ack`) is the standing-approval acknowledgement. The agent acknowledges a message that has *just arrived*, with a reply or reaction from content the person pre-approved by digest. The gate picks the target itself, and a randomised 5–30 s pause comes before the act (`slack/src/operations/ack.ts:56-79`). Its activity line records `{acknowledged ts, channel id}` and the reply ts (`activity.ts:302-311`), and the ledger keeps channel, ts and thread. **This one does join** to a Slack event (`channelId/ts`).
- The event service's own "told" lines name only the rule, account, target and count. They deliberately carry **no event id** (`events-daemon/src/runtime/delivery-activity.ts:12-20`).
- The event service's MCP tools (`events_lane_item`, `events_queue_done`) write **no activity line**: `recordActivity` is used only in `delivery-activity.ts`. Queue `done` and `dismiss` store a state and a time with **no actor** (`runtime/queue.ts:461-478`), so "done by the window" and "done by the person in the app" look identical.

**What joins today**
- Inside the event database: delivery → decision → event → `dedupe_key`, which contains the Gmail messageId or the Slack channel/ts. This covers "arrived → matched → judged → delivered/queued". No operation exposes it: `deliveries list` has no `decision_id` or event id, and `queue items/list` has no event id or delivery id (`queue.ts:63-83,692-705`).
- Across stores: a Gmail **messageId** (event ↔ activity read lines) and a Slack **channelId+ts** (event ↔ ack ↔ thread reads).
- `activity show` works per session only (`activity.ts:940`). No query asks "which sessions touched item X", so the app would have to read every session in range.

**Missing for an "Inbox timeline"**
1. An owner read, content-free, per event: `eventId`, type, account, times, the source key, each rule's outcome and judge answer, each delivery's target kind and state, and the queue item's id and state. Ingest keeps no Gmail **threadId** (only encrypted projections do), so a thread view needs a new column.
2. Activity lines that link replies: the replied-to messageId on `gmail.draft.reply`, the threadId on sends, `thread_ts` on Slack posts.
3. An activity query by item id across sessions.
4. Event-service activity lines, or an actor on queue changes: woken, lane item read, done by window or person.
5. A person's own Gmail reply is visible only by asking Google (`gmail_thread_timeline`, `capabilities.json:828-832`) or through a `gmail.message.sent` rule.

**Feasibility:** medium to large. Most of the data exists but sits in three places: the event DB (not exposed), the activity log (no reply links) and the Slack ledger. All of it is ids and times, so it stays content-free.

## E. "Agent Comms Test" looks the same as the real app
